# consoled-e2e

BORUIX 的**端到端验收程序**，验证控制台字节环的**阻塞-唤醒往返**在真实用户态下正确工作。

[English](README.en.md)

## 测什么

程序分两个角色（由启动参数区分），经**真实系统调用**跑完一次完整的控制台数据往返：

| 角色 | 行为 |
| --- | --- |
| `writer` | 后台进程：阻塞读取控制台（空环时挂起）→ 收到 12 字节片段后逐字节校验 → 再挂起等第二段 → 校验 → 写 PASS 标记 → 退出 |
| `consumer` | 前台：等 `writer` 就绪 → 写入两段片段 → 确认消费水位归零并对账 → 终止 `writer` → 收尸 → 核对 PASS 标记 |

两段测试片段跨 `0`/`255` 边界、段间内容不同，因此**次序错乱必然暴露**。

## 为什么需要独立程序

内核自检直接调节点与环形缓冲，**触及不到**两条关键路径：

1. **系统调用封装本身**——参数打包、错误码翻译、用户缓冲校验；
2. **真实的阻塞-唤醒往返**——等待者的挂起与唤醒要求真正的进程上下文切换，只能在有进程上下文的
   用户态进程里验证。

## 判定形态

当前控制台服务的守护进程尚未常驻，控制台环的**唯一写者是本程序自己**（`writer` 角色）。这把
"写端 → 等待者唤醒 → 读端交付"这条内核链路隔离成了**单变量的可判定实验**。待守护进程接管写端
后，真实终端流再由更上层的交互验收覆盖。

## 用法

由协调端拉起两个角色（`consoled-e2e writer` 等）。退出码即裁决。

## 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 全部正确 |
| 非零 | 任一步骤失败 |

## 构建

```bash
cargo build --release
```

```
├── linker.ld     # 用户态段布局
└── src/
    └── main.rs   # 写端与读端逻辑
```
